# Hawkeye core

The Windows and Linux architecture is described in [the portable desktop design](docs/PORT_DESIGN.md). The Swift design below remains the macOS implementation and the behavior reference for the port.

The domain is a `TodoTask`, a durable `TaskState`, and one pending write per task. Completion is derived from `completedAt`. `dueAt` stores the scheduled start in Hawkeye. A local duration override does not enqueue remote writes. Remote identity includes the project and a task ID allocated once before the first create request.

Two ownership options were considered.

1. The UI owns state and passes snapshots into a sync worker. This makes binding convenient, but every response needs a revision handshake with the UI and disk writer. A response can otherwise replace an edit made while networking awaited.
2. One `TaskService` actor owns state, disk writes, and sync. The UI requests mutations and reads snapshots. Networking suspends the actor, so user edits remain available. Response acknowledgements remove only the exact pending operation sent. This is the chosen design.

`TaskState` contains pure mutations and merge rules. `TaskService` persists a new state before adopting it. JSON writes are atomic and versioned. An unsupported schema or corrupt file fails visibly rather than resetting the task list. No authentication credential appears in task persistence.

All local tasks have a durable create intent. They upload automatically once a client and destination project are configured. A client without a destination downloads tasks but leaves local creates queued. Existing remote edits retain their original project.

Sync sends the queued writes first, then reads every task project. A second sync invocation returns a skipped report while the first is running. A create writes its stable remote ID to disk before contacting TickTick and checks that exact ID before retrying. Creation confirmation is saved before completion is requested. Edits arriving during any request retain their newer pending operation. Missing records are fetched individually for their actual status. A missing or inaccessible remote record is retained locally.

The explicit create ID is sent to TickTick's Open API. Its acceptance is covered by a deterministic server fixture, not a real account test. The documented API does not promise a general idempotency key. The application must surface a failed create instead of generating a new remote ID on retry.

The `TaskServicing` protocol is the application boundary for future automation or AI commands. The HTTP transport is injectable for deterministic tests. There is no network background loop in the core. The UI schedules `sync()` every 60 seconds.

The editor update command changes only title, description, scheduled start, and duration on the latest stored task. Completion and user pause have separate commands, so saving an older editor cannot undo either action.

The client paginates the official project endpoint and imports Inbox tasks through `POST /task/filter`. It requests the last 30 days of completed tasks on first sync through `POST /task/completed`. Subsequent history queries begin 60 seconds before the previous successful history cursor. Failed history requests keep the cursor for retry. Inbox and history endpoints cap results at 200; reaching a cap produces a visible warning. Known tasks missing from these results are still checked individually. A failed list produces a warning while other lists continue importing. A 401 aborts the sync. No private endpoints or guessed completion states are used.

`TaskFocusController` is a pure state machine owned by `TaskService`. `evaluateFocus(at:)` selects one unfinished task inside its half-open scheduled interval. Priority is start, creation time, then UUID. The controller emits typed activation and deactivation events only on transitions. Its staged state and `UserFocusState` are adopted only after any required disk write succeeds.

`TaskState.userFocus` holds the user-level snooze, the IDs that consumed their one pause, and the last announced start per task. Existing JSON without this field loads an empty user model. Old per-task snooze fields are ignored. Pause suppresses every candidate without moving task dates. A pause survives completion or deferral of its originating task until its own expiry. A resumed or restarted occurrence does not repeat its start alert. A deferred occurrence can send a new alert while keeping its used pause allowance.

`startNow(id:at:)` validates current activity and commits the new task start and user focus in one actor transaction. It rejects a task that is already active or conflicts with another active task. The command ends a global snooze and records a `ManualTaskStart` containing the task ID and exact scheduled start. This occurrence takes priority over earlier overlapping tasks until completion, expiry, or rescheduling. Pause preserves that selection and the used pause IDs. The returned transitions are published once by AppModel before its normal snapshot refresh. TickTick dates are written at whole-second precision, so a remote merge preserves the existing local start if both dates serialize to the same timestamp. This prevents a manual start from losing its selection or sending a duplicate alert on sync.

AppModel broadcasts `TaskFocusEvent` through `focusEvents`. One subscriber updates the eye's published active-task ID and logs transitions; another sends macOS notifications. New side effects can subscribe without adding policy to the views. A cancellable timer sleeps until the next start, end, or snooze boundary, with a 30-second clock reconciliation limit. Wake and clock changes also trigger evaluation. Remote sync remains on its independent 60-second loop.

`PomodoroTimer` is a pure value in HawkeyeCore. It stores validated focus and break durations, an optional running session, and its current phase interval. AppModel owns its independent one-second tick and invokes the same reconciliation after wake, clock changes, and activation. Phase boundaries derive from the session start and captured durations. Reconciliation skips whole cycles arithmetically and emits at most one current-phase alert. Start and Stop are idempotent. Configuration changes apply on the next Start. Normal builds store duration preferences separately from task data. Isolated sessions use `pomodoro.json` in their data directory. Relaunch starts the timer idle.

`TaskNotifications` owns both notification types with separate cancellable jobs and identifiers. Pomodoro focus completion starts a break and sends a hydration reminder. Break completion starts focus and sends another alert. Stop removes the latest pending Pomodoro request and rejects delivery that finishes after cancellation. Existing task notifications remain independent.

`AppModel` derives one `MonitoringSession` for both monitors. A running Pomodoro takes precedence over the authoritative `TaskFocusUpdate.activeTask`. Otherwise, the active task supplies its scheduled window. Pomodoro has a stable session ID across phases and stays active until stopped, independent of task pauses, completion, or clock changes. Each Pomodoro monitoring operation gets a finite 30-second deadline. Task monitoring retains its scheduled deadline.

`DistractionMonitor` receives that session from `AppModel`. Transition events alone are insufficient because editing duration can update an active occurrence without emitting an event. The monitor owns one cancellable polling task on the main actor. Policy, task, and detector changes invalidate its generation, cancel current work, and wait for the previous inspection to finish before starting another. Late results are discarded even when cancellation is delayed. Every asynchronous observation must still match the current generation, deadline, and foreground process before an effect can run. Restored active occurrences start monitoring independently of the notification flag.

`DistractionDetecting` is a Sendable async contract. `DetectionContext` contains the monitoring session, policy, deadline, and foreground process. `DetectionReport` returns typed app or browser-tab findings, an observation-only possible distraction, an unavailable capability, or a fixed failure category. It contains no screenshot, OCR text, prompt, or model response. `MonitoringMethod` identifies deterministic, OCR, and VLM methods, but only `DeterministicDistractionDetector` is implemented. Its read-only `DeterministicObservation` dependency supplies Automation status and browser tabs. `DistractionActions` supplies foreground identity and guarded native actions separately, so other detectors do not need browser-reading methods.

To add a method, implement `DistractionDetecting` with its own dependencies and positive `pollingInterval`. Keep capture or inference off the main actor, bound its work, check the context deadline, and cooperate with cancellation. Return findings to the coordinator for logging and enforcement. Inject the detector through AppModel or replace it with `updateMonitoringDetector`. Replacement also adopts its polling interval unless the monitor has an explicit composition override.

The coordinator owns all logging, retry suppression, and enforcement. It validates each finding against the current foreground process and blacklist again. A blocked whole app takes precedence over tab actions. A tab requires a supported browser, exact identity and URL, a matching configured domain, and current Automation access. Classification without an exact approved target only produces a fixed observation message. Typed suppression targets and outcomes distinguish retries, recovery, and changed safe failure reasons. Detector text and arbitrary error descriptions never enter activity logs.

`DistractionSettings` owns the typed app and website policy. Defaults block `com.apple.Chess`, `org.mozilla.firefox`, and `instagram.com`. The bottom-right configuration panel adds applications by bundle identity and canonical website hosts. Changes persist before publishing and immediately invalidate monitoring observations. Development and release preference domains stay separate. An isolated data directory uses its own `focus-policy.json` and never reads or writes the normal blacklist. The independent `ScriptableBrowser` registry describes Safari and Google Chrome capabilities. Adding a block requires no monitoring-loop changes. Adding a browser requires an adapter whose tab identity and close semantics are verified against its scripting dictionary.

Native effects identify the foreground app through `NSWorkspace.frontmostApplication` and terminate a blocked app only after checking its bundle ID and process ID again. When a supported browser is foreground and has Automation access, a bounded background `osascript` process reads tabs across its windows. Pure Swift policy matches actual HTTP or HTTPS hosts, including normalized case, ports, and a trailing DNS dot. URLs and titles are never logged. JXA receives only an already approved tab observation for a close, then rechecks the foreground process, deadline, and exact current URL. Chrome uses stable window and tab IDs. Safari uses a stable window ID and tab position, processed in reverse order. The final URL check cannot make Safari's separate read and close AppleEvents atomic. A delivered AppleEvent cannot be withdrawn even after its sender is cancelled.

`BoundedCommandRunner` runs process launch, pipe reads, and waiting off the main actor. It discards stderr, caps stdout at 2 MiB, and terminates commands after four seconds or cancellation. A process that ignores termination receives SIGKILL after 200 ms. Outputs remain in memory. The monitor never retries a stale close. Fixed command failures remain visible while repeated messages for the same failing target are suppressed.

`ScreenshotMonitor` receives the same monitoring session independently of distraction detection. It starts sampling after 60 seconds and waits another 60 seconds after each capture finishes. Task ID and scheduled start identify an occurrence. Title and duration edits update the current eligibility without resetting an active cadence. Without a running Pomodoro, task pause, expiry, rescheduling, and replacement cancel the session. Pomodoro phase changes preserve the session and capture cadence. One capture runs at a time; a replacement waits for previous work and discards late results before any attachment is written. A naturally expired session becomes idle, so extending that occurrence can start a new cadence.

`ScreenshotCapture.swift` defines the capture data and `ScreenshotCapturing` boundary independently of scheduling and processing. `ScreenshotCapturing` returns per-display capture outcomes. `MacScreenshotCapture` enumerates the connected displays for each sample, so display changes take effect at the next sample. Each successful screenshot carries its display identity, capture time, full image, thumbnail, and on-screen window metadata. Window-to-display association uses frame intersection and exact process identity. An on-screen window can be occluded by another window. Metadata does not prove that a window has uncovered pixels. A failure on one display does not discard captures from the others.

The native source runs only in an enabled packaged session. It preflights Screen Recording without prompting and checks cancellation and the deadline around asynchronous work. ScreenCaptureKit captures each display without cursor or audio. The full image remains in memory for processing. Only a JPEG thumbnail with a maximum 480-pixel edge is persisted. The monitor checks the latest monitoring session again before persistence or enforcement. macOS work already started cannot be undone by cancellation, but its result can be discarded.

Each display runs an independent analysis through an ordered list of injected processors. Results from an earlier step are available to the next step for that display. This permits an OCR step followed by an LLM step without sharing text or classifications between displays. The built-in processor checks on-screen application windows against the current blacklist. No OCR or model inference is implemented. Policy revisions invalidate pending analysis without restarting the screenshot timer. A persistence failure does not suppress evaluation.

To extend that chain, implement `ScreenshotProcessing.process(_:analysis:)` and pass the ordered list through `AppModel`'s `screenshotProcessors` argument. Both the normal and injected initializers accept it. Direct monitor callers use the `processors` argument. `ScreenshotPipeline.defaultProcessors` defines the default chain once. An explicit list replaces that chain; include `BlacklistedApplicationProcessor()` to retain screenshot blacklist checks. `ScreenshotProcessingContext` supplies the display image, display frame, captured windows, task, policy, and deadline. Add a concrete typed result to `ScreenshotAnalysis` when introducing OCR or another intermediate representation. Later processors consume that result from their `analysis` argument. The current analysis contains typed observations and action proposals. Keep text and model responses in memory and out of activity logs. A failed processor preserves earlier results, so a dependent stage must check that its required input exists.

`ScreenshotMonitor.Sample` groups captured window evidence, the policy and deadline snapshot, and attempted actions for one sample. Its private `enforce` method validates proposals and deduplicates attempts across displays. Live session and revision checks remain in the monitor, including checks after asynchronous revalidation. A separate enforcement coordinator would require authorization callbacks without serving another caller. Processor extensions use the existing pipeline, and foreground detector extensions use `DistractionDetecting`.

Screenshot findings propose exact actions. Whole-app termination requires an app explicitly present in the current blacklist, captured window evidence, and fresh native process and display checks. A future browser classification must resolve the captured window to a unique browser window and selected tab. ScreenCaptureKit window IDs and browser scripting window IDs are separate identities. Tab closure requires the same window association, exact tab identity, unchanged URL, current Automation access, and a current task and policy. An ambiguous match is non-actionable. A browser classification never becomes whole-browser termination.

`ScreenshotObservationProviding.visibleTab` is a read-only observation of the current selected tab. A future classifier must bind that observation to the image evidence it classifies, rather than attach a newly selected tab to an older screenshot. The resolver alone does not prove that correspondence. The native route rejects multiple running browser instances with the same bundle ID and ambiguous window bounds. Browser state can still change between separate read and close AppleEvents, as with foreground tab enforcement.

`ActivityLog` is the only screenshot writer. An `ActivityEntry` has an optional `ActivityScreenshot` containing a file URL, capture time, and display identity. JPEG data stays out of retained entries. The adjacent `activity.screenshots` folder uses mode `0700`; UUID-named JPEGs use `0600`. Startup and insertion prune the oldest recognized regular JPEGs to 240 in total across displays, preserving other files and symlinks. Text entries identify the display and contain a relative thumbnail path. An attachment is published only after its JPEG and text entry are saved; persistence errors produce a visible failure instead. The developer activity view renders at most 240 by 150 points, opens the local file on click, and handles older pruned attachments without a preview.

`BrowserContentMonitor` receives the same `MonitoringSession` independently of screenshots. It retrieves foreground Safari or Chrome accessibility text immediately, then once a minute after each attempt. `MacBrowserContentCapture` confines native AX objects to one bounded serial worker and revalidates the selected page. `BrowserContentExtraction` preserves text values and derives main content only from an unambiguous main landmark or article. There are no per-site rules or filters. `ActivityLog` writes private, retained JSON sidecars with the session identity and full/main text. Plain text logs contain attachment references only. The activity window loads text on expansion and is available in both build configurations. See [macOS browser text](docs/MACOS_BROWSER_TEXT.md).

`FocusPermissions` owns first-launch consent and recoverable status separately from task activity. Notification consent uses the existing notification owner. Screen Recording enables local task screenshot thumbnails. Accessibility enables native browser text capture. Neither Screen Recording nor Accessibility gates native foreground detection. Browser Automation is preflighted in process with `AEDeterminePermissionToAutomateTarget`, which requires an already running target. Consent and Screen Recording requests run off the main actor. First-time browser requests are recorded in preferences to avoid poll-time prompts; new browser launches and app activation refresh status. No browser is launched for consent. The signed app's Info.plist supplies `NSAppleEventsUsageDescription`. The current nonhardened, nonsandboxed signing setup needs no Automation entitlement.

The default effects in the injected AppModel initializer are disabled, and its screenshot monitor exists only when a fake source is explicitly supplied. Isolated data-directory runs and bare executables have no native screenshot monitor. Isolated sessions also disable notifications, permission requests, workspace inspection, browser scripting, and app termination while retaining a readable permissions panel. Tests use fake sources for lifecycle races and synthetic JPEGs for screenshot persistence. Pure JXA operations run against in-memory browser fixtures. Live screen capture, TCC consent, and browser interaction remain manual checks of the signed normal app, separate from isolated UI validation.

For imported tasks, TickTick `startDate` takes precedence over `dueDate` as the scheduled start. A positive difference between those dates supplies `remoteDuration`; the local duration override takes precedence, followed by the 30-minute default. Updating a ranged task shifts both remote dates by the same amount. Tasks represented only by `dueDate` retain that representation. Start-time edits convert all-day tasks to timed tasks; unrelated edits preserve the all-day setting.

Completion uses the dedicated completion endpoint. A generic task update preserves an existing completed status while that endpoint runs. Reopening uses a status update because TickTick does not document a dedicated reopen endpoint.

Queued local task fields take precedence over downloaded task fields until the upload is acknowledged. This is a task-level conflict policy. The service preserves TickTick fields outside the local model, including checklist items, recurrence, tags, and sort order. User snooze and local duration overrides remain local.

The throughput checkpoint is a passing test suite for disk round trips, offline retries, ambiguous creates, edits during requests, overlapping polls, remote completion, and local-field preservation. UI work can proceed independently against the public actor API.

Endpoint definitions were checked against the [official TickTick API markdown](https://developer.ticktick.com/docs/openapi.md) on 21 October 2026. Live account sync is not part of the deterministic test suite.
